# 设计说明

面向实现和维护人员解释边界、模块职责、交互、约束、异常路径及验收方式。首先区分“记录现有实现”与“提出新设计”；前者对照代码，后者明确提案和未决问题。

对应契约：`word_skills/schemas/design-spec.yaml`。

| ID | 应回答的问题 |
|---|---|
| requirements | 需求、角色、使用场景与非目标 |
| constraints | 已有环境、数据、接口、部署与兼容约束 |
| architecture | 模块职责、依赖方向、核心数据流与选择理由 |
| interfaces | 实际入口、输入输出、数据模型及错误处理 |
| deployment | 安装依赖、执行路径、失败恢复和运维边界 |
| acceptance | 可观察的验收条件、证据需求、风险和待决问题 |

借鉴 technical-writer 的设计审阅方法：重要选择同时解释目的、代价、合理替代方案及限制；不机械为每个普通选择添加固定框。已有行为必须读实现；推测调用链需要进一步核查。

源码引用应包含可复核位置与快照。函数存在只能证明定义存在；要宣称运行可用，应有实际调用结果。接口字段和代码标识符保持原样，不能为了中文行文改写 API 名称。
