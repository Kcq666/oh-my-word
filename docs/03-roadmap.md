# 实施顺序与验收

状态更新：2026-10-15。本轮已经完成技术文档 P0 与专利兼容整合的可交付切片；仍未实现的能力继续标为 planned。路线图保留目标架构和后续验收条件，不把目录、路由命中或结构检查当成业务能力完成。

## 阶段 A：完成技术文档技能的首条可用链路（已完成）

已交付 `oh-my-technology` 与 `word-document` 两个实现技能，保留原专利业务门禁作为兼容后端；没有为未实现模式创建空 Skill。

交付：

1. 完整 `oh-my-technology/SKILL.md`，覆盖新写、改写、审阅、已有文档补充的范围判断。
2. `technical-report`、`design-spec` 两种已实现模式的章节契约与写作参考；其余五种仍是目标模式。
3. JSON v1 来源、引文、章节与证据映射契约，以及显式缺口处理。
4. JSON v1 草稿、共享 CLI、默认 Word 版式及受限的 `style`/`slots` 模板适配、内容与版面检查。
5. 两种模式的合成测试样本和缺材料失败路径；合成数据不当作真实项目结论。

实施取舍：技术文档使用 MarkItDown 与独立来源定位，专利保留原摄入和渲染门禁；两条路径共享事实保真与变化失效原则，不混用未经核实的审阅状态。

验收结果：JSON v1 来源/证据/章节契约、DOCX 生成、PDF/页图检查、审阅记录和缺口状态已有代码与回归测试；单节参考样式与显式插槽 fixture 已验证。复杂企业模板、所有 Office/WPS 版本、真实业务写作质量仍需后续样本验证。

## 阶段 B：整合 Word Skills 总仓库（本次切片已完成）

已交付 `word-skills` 总入口、`word-document` 制作技能、共享 Python 包、注册表、兼容入口、专利资源迁移和最小安装说明；本次提交完成干净构建、包外运行、暂存清单审阅，并推送到用户指定的 `oh-my-word` 远端。

迁移步骤：

1. 记录现有 Git 状态和受影响文件快照，明确未提交修改都属于迁移输入；保留原输出目录和用户材料。
2. 在可回退的开发分支或副本中整理路径；旧 Python 包及 `tools/patent.py` 暂时保持兼容。
3. 用明确路径迁移专利 Skill、prompts、references、六个领域模块，并更新所有引用和注册表。
4. 新共享包先供技术文档使用，再逐项替换专利的共用函数；每次以既有专利测试验证行为。
5. 完整安装后，从其他工作目录执行旧 CLI 和新 CLI；检查模板、图片、技能引用和包数据能否定位。
6. 维护态 monorepo 验证后再制作独立分发包；不要因为根目录改名就宣称支持任意技能安装器。
7. 代码、文档和安装验证就绪后提交并推送到用户指定的 `open-agent-power/oh-my-word`；远端当前未返回可见分支，推送时不覆盖已有历史。

验收结果：旧专利测试与门禁回归保持通过；新 CLI、注册表、技术文档管线和兼容入口已有测试；已从仓库外验证安装 wheel、旧/新 CLI 和结构检查。

## 阶段 C：项目申请书

先实现通用项目申请，再选一个真实受理渠道做完整 Profile。

交付：指南/要求清单、项目目标、研究或实施任务、技术路线、里程碑、可行性、团队基础、预算说明和附件清单；全部可以按官方模板改写或填充。

验收重点：

- 指南编号、年度、适用类别和模板版本可追溯；过期或不完整指南明确标记。
- 要求 → 章节 → 附件的映射能查出遗漏；字数和页数分别在正文与最终产物中检查。
- 预算子项、汇总和正文数值一致；比例规则来自本次指南，不内置“一套全国通用预算”。
- 目标、计划、已有成果分开；不虚构团队经历、合作承诺、审计数字或测评结果。
- 缺单位或人员资料时交付待补草稿，不编造表单字段；当前申请渠道对辅助写作的要求另核对。

## 阶段 D：软件著作权

以 Fokkyp 的业务流程与脚本为选定候选，完成逐文件审读和来源记录后再吸收。

交付：项目功能证据、申请字段草稿、源码候选与选择理由、代码材料、操作说明、截图与材料清单。Word 输出使用共用后端；如有足够证据再引入额外后端。

验收重点：

- 代码材料能映射原始文件、行范围、版本和哈希；不以换行/补写凑页数。
- 排除密钥、第三方依赖与构建产物；选择规则要能说明哪些内容属于待登记软件。
- 名称、版本、日期、权利人、手册内容和代码材料一致；不能从代码自动推断权利归属。
- 手册来自真实功能与界面，截图缺失或界面无法运行须明确记录。
- 官方当期材料规则在实现时核对，页数/行数配置与最终渲染结果分别检查，不以字符估算代替实际分页。
- 若涉及前端页面检查，按项目 AGENTS.md 实际运行页面并截图检查，不从代码推断界面。

## 验证分层

| 层次 | 验证内容 | 通过意味着什么 |
|---|---|---|
| 技能结构 | frontmatter、路径、引用、注册表、安装包完整性 | 能加载，不等于会正确写作 |
| 代码与契约 | 输入格式、哈希、引用、预算合计、源码映射、失败分支 | 机械逻辑正确，不等于语义充分 |
| 真实产物 | DOCX 内容、模板结构、表格、图题、页眉、页码及渲染页 | 在已测引擎下输出可用，不泛称全部 Office/WPS 版本 |
| 行为评测 | 真实/合成任务中的路由、事实保真、内容完整性和缺口处理 | 有记录的场景质量证据，不保证其他场景 |

首轮建议覆盖 12 个任务场景：完整技术报告、无测试数据报告、已有设计说明改稿、需求验收条件、接口与代码不符、失败用例测试报告、真实页面操作手册、运维版本差异、指南缺失申报、预算不一致、源码不足软著、已有专利修改后旧审查失效。它们是计划案例，不是已经通过的测试。

每次运行保存输入版本、实际输出、问题和修复记录。若使用独立评测 Agent，按当前任务授权和环境执行；不将多 Agent 设为使用所有技能的强制条件。

## 完成标准

完整技能应当同时具备入口、按需参考、必要模板/脚本、清楚的能力边界以及真实产物验证记录。只有一份长 SKILL.md，或只有一个能把文本写入 DOCX 的脚本，都不足以称为完整文档撰写能力。

第一轮实施优先完成技术文档；其余业务以明确的阶段推进。暂不增加 GUI、在线账号系统、自动申请提交、全量知识库或不必要的外部服务依赖。
